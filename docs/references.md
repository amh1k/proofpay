# ProofPay — Reference Repositories

These repos are for **studying patterns and lifting specific ideas** — a data model, a pipeline order, a threshold-calibration method — not for wholesale copying. Read the named file or module, take the design, write our own version against our own tests. Two practical rules for a judged competition: (1) **license matters** — GPL-3.0 repos (erpnext, sherloq) are read-only design references and must never have code vendored into a permissively-licensed backend, and repos marked `NONE`/`NOASSERTION` have no grant at all, so treat them as architecture reading only; (2) prefer the MIT/Apache/BSD dependencies flagged below as *actual dependencies* over reimplementing them badly under time pressure.

## 1. Reconciliation & matching engine

The heart of ProofPay. Everything here is about candidate retrieval, per-field scoring that decomposes, and allocation that cannot be silently reused.

| Repo | Stars | License | What to take |
|---|---|---|---|
| [moj-analytical-services/splink](https://github.com/moj-analytical-services/splink) | 2.4k | MIT | The Comparison / ComparisonLevel data model: each field is a Comparison with ordered levels evaluated top-down, first match wins, yielding a discrete labelled outcome ("exact", "jaro_winkler >= 0.9", "amount within 1%", "timestamp within 15 min", "else"). See `comparison_level_library.py` and `blocking_rules`; steal the match-weight waterfall as the evidence-breakdown UI. |
| [frappe/erpnext](https://github.com/frappe/erpnext) | 38k | GPL-3.0 | **GPL — read for design, do not copy code.** `bank_reconciliation_tool.py`: an additive rank summed from named per-field indicators (exact amount, party name, reference number, date proximity), plus the allocation model — `unallocated_amount` on a transaction with a child allocation table, so a consumed transaction cannot be reused. Implement DUPLICATE that way, as an allocation row with a uniqueness constraint, not a heuristic. |
| [opensanctions/nomenklatura](https://github.com/opensanctions/nomenklatura) | 262 | MIT | `nomenklatura/matching/`: a `ScoringAlgorithm` registry of named, **versioned** algorithms, each declaring `Feature` objects (name, weight, description, `compare()`) and returning a result carrying the score plus per-feature sub-scores. Persist algorithm name+version on every reconciliation row. Also `blocker.Index` for phonetic/token blocking. |
| [dedupeio/dedupe](https://github.com/dedupeio/dedupe) | 4.5k | MIT | `dedupe/predicates.py` — composable, cheap, hashable blocking predicates that emit block *keys* so retrieval is a dict lookup, not an O(n) scan. Key on last-6-of-ref-id, rounded amount, date bucket, normalised name tokens, and union the buckets. Also its explicit missing-field handling: OCR will drop fields and the scorer must degrade, not crash. |
| [J535D165/recordlinkage](https://github.com/J535D165/recordlinkage) | 1.1k | BSD-3-Clause | The `Compare` API shape: register comparators per field, get a comparison-vector DataFrame (one row per pair, one column per field, 0..1). `compare.numeric(method='gauss', offset=, scale=)` is the right answer to timestamp and amount tolerance — `offset` is the free window, `scale` the decay — far better than a hard ±15-min boolean. *Stale: no pushes since Feb 2024.* |
| [AI-team-UoA/pyJedAI](https://github.com/AI-team-UoA/pyJedAI) | 101 | Apache-2.0 | The staged workflow where every stage is swappable with a uniform `.process()` / `.evaluate(ground_truth)` returning precision/recall/F1. Adopt as our **test architecture**: report metrics per stage so a miss is diagnosable as retrieval failure (never entered the candidate set) vs scoring failure (retrieved, ranked too low). |

**Read first: splink.** Open `splink/comparison_level_library.py` and `comparison_library.py` (`DateOfBirthComparison` is the template for a `TimestampComparison`) — that ordered-levels-first-match-wins structure is directly our decision-rule and evidence-breakdown format, and it gives us discrete labelled outcomes instead of an opaque float.

## 2. Fuzzy name matching & normalisation

"Muhammad Ali" ~ "M. Ali" is a named requirement in the spec. Transliteration, not typos, is the actual problem.

| Repo | Stars | License | What to take |
|---|---|---|---|
| [rapidfuzz/RapidFuzz](https://github.com/rapidfuzz/RapidFuzz) | 4.1k | MIT | **Make this a real dependency, not a reference.** `fuzz.token_set_ratio` / `token_sort_ratio` for reordered and extra tokens, `partial_ratio` for OCR truncation, `distance.JaroWinkler.similarity` for prefix weighting. The load-bearing API is `process.cdist` / `process.extract` with `score_cutoff` and `scorer=` — one vectorised call shortlists a claim name against N candidates. MIT, unlike GPL fuzzywuzzy. |
| [jamesturk/jellyfish](https://github.com/jamesturk/jellyfish) | 2.2k | MIT | `metaphone()` / `nysiis()` as a **phonetic blocking key** per name token, stored alongside each merchant transaction so Mohammed/Muhammad/Mohd land in one bucket; `jaro_winkler_similarity()` for the per-token score. The pattern to borrow is the split: phonetic key for RETRIEVAL, Jaro-Winkler for SCORING. No model to ship. |
| [anhaidgroup/py_stringmatching](https://github.com/anhaidgroup/py_stringmatching) | 144 | BSD-3-Clause | Monge-Elkan (scores each token of A against its best-matching token of B) and Soft-TFIDF (down-weights ubiquitous tokens — "Muhammad" should contribute far less evidence than a rare surname). That down-weighting is a genuine correctness property a plain ratio gets wrong. Also its `QgramTokenizer` / `AlphanumericTokenizer`. |
| [DeNederlandscheBank/name_matching](https://github.com/DeNederlandscheBank/name_matching) | 170 | MIT | `name_matcher.py`'s retrieve-then-score split: TF-IDF over char n-grams + sparse cosine to pull top-N in one matrix multiply, then rescore only those N with a configurable metric ensemble, then return match + score + which metric fired. Makes retrieval matrix work rather than pairwise. |
| [opensanctions/rigour](https://github.com/opensanctions/rigour) | 66 | MIT | The `rigour.names` module: case/diacritic/punctuation folding, transliteration, tokenisation into name parts, curated honorific/prefix strip-lists. Take the principle that normalisation is a separate unit-testable stage with a persisted `normalised_name`, so evidence shows both the raw OCR string and the form actually scored. Extend the honorific list with Mr/Mrs/Malik/Syed/Sheikh/Ch./Hafiz/Haji. |
| [Christopher-Thornton/hmni](https://github.com/Christopher-Thornton/hmni) | 268 | MIT | Its documented failure modes of naive fuzzy matching on transliterated and abbreviated names (single-initial expansion, dropped honorifics, vowel drift) — lift those straight into a parametrised pytest table for the name scorer. Also the `similarity()` / `.dedupe()` / `.record_linkage()` API shape. *Dormant: no pushes since Jun 2024 — design source and benchmark, not a dependency.* |

**Read first: RapidFuzz**, but only its `process.cdist` docs — then spend the real reading time on **jellyfish**'s phonetic encoders, because the phonetic-key-for-retrieval / Jaro-Winkler-for-scoring split is the single design decision that makes Pakistani transliterated names tractable, and it costs two function calls.

## 6. Duplicate & reuse detection

The DUPLICATE state has two halves: the same *image* resubmitted, and the same *transaction* allocated twice (see erpnext, §1).

| Repo | Stars | License | What to take |
|---|---|---|---|
| [JohannesBuchner/imagehash](https://github.com/JohannesBuchner/imagehash) | 3.9k | BSD-2-Clause | **Dependency, day one.** `phash()` (DCT-based, survives WhatsApp recompression) plus `dhash()` as an independent second hash, both stored as hex on the claim row. Specifically borrow `crop_resistant_hash()` — it survives the status-bar trim a customer does when re-sending an old screenshot, which plain pHash does not. Copy the `ImageHash.__sub__` Hamming idiom so distance is a plain int the rules can threshold. |
| [idealo/imagededup](https://github.com/idealo/imagededup) | 5.7k | Apache-2.0 | Solves what imagehash doesn't: corpus-wide retrieval. The encoding-map + BKTree pattern under `imagededup.handlers.search`, behind `PHash().find_duplicates(encoding_map=..., max_distance_threshold=N)`, so "has this screenshot been used before?" is a tree lookup, not a full scan per upload. Also its `evaluation` module's precision/recall harness. |
| [thorn-oss/perception](https://github.com/thorn-oss/perception) | 201 | Apache-2.0 | The `perception.benchmarking` package: apply a transform suite (JPEG recompression, crop, pad, watermark, resize) to seed images and report each hash's distance distribution, so the Hamming threshold is picked at a *measured* false-positive rate. Run it over ~50 real screenshots to produce a defensible `DUPLICATE_HAMMING_MAX` constant for the versioned ruleset. |

**Read first: thorn-oss/perception's benchmarking module** — not imagehash. Calling a payment DUPLICATE accuses a customer of fraud, so the asymmetry matches Thorn's, and walking into a demo with a threshold justified by a measured false-positive curve rather than a guessed constant is worth more than the detector itself.

## Recommended reading order

1. **[moj-analytical-services/splink](https://github.com/moj-analytical-services/splink)** — Start here, before any code. `comparison_level_library.py` fixes the shape of the whole engine: fields as Comparisons, ordered levels, first match wins, a discrete labelled per-field outcome. Every later decision depends on this data model existing.
2. **[frappe/erpnext](https://github.com/frappe/erpnext)** (`bank_reconciliation_tool/`, GPL — design only) — Read immediately after splink. It supplies the two things splink doesn't: an additive inspectable rank built from named per-field indicators, and the allocation table that makes DUPLICATE a database constraint rather than a heuristic. Settle the allocation schema before writing migrations.
3. **[fastapi/full-stack-fastapi-template](https://github.com/fastapi/full-stack-fastapi-template)** — Once the domain model is decided, this gives persistence and API for free: `backend/app/tests/conftest.py`, the Alembic wiring, and the deps aliases. Come here now so the engine gets pinned by real tests while it is still small.
4. **[invoice-x/invoice2data](https://github.com/invoice-x/invoice2data)** — With the engine consuming a stable PaymentClaim, build the producer. `extract/templates/` plus `validators.py` give per-provider Easypaisa/JazzCash/Raast templates as versioned YAML and a clean extraction-success gate feeding NEEDS_REVIEW.
5. **[QwenLM/Qwen3-VL](https://github.com/QwenLM/Qwen3-VL)** (`cookbooks/document_parsing.ipynb`) — Now wire the Alibaba-native extractor behind the template layer, with `smart_resize()` for reproducibility. It comes after invoice2data deliberately: the deterministic template path is the fallback the demo cannot afford to be without, so build it first and let the VLM be the upgrade.
6. **[satnaing/shadcn-admin](https://github.com/satnaing/shadcn-admin)** — Last. Clone the shell, retarget the data-table status facet to the five states, and spend the remaining time on the expandable evidence row rather than on chrome.
