# Running the demo

Everything here has been run on a clean clone. If a command below does not work, that is a bug in
this file, not in your setup.

The demo needs no API key, no database server and no internet. That is deliberate: every cloud
service in ProofPay sits behind an adapter with a working local implementation, so a missing
credential degrades quality and never breaks the product. On a projector at a venue you do not
control, that is the difference between a demo and an apology.

---

## Setup, from nothing

You need [uv](https://docs.astral.sh/uv/) and Node 22. Not even Python: uv installs that itself.

```bash
git clone https://github.com/amh1k/proofpay.git
cd proofpay
```

**Frontend**, in one terminal:

```bash
cd frontend
npm ci
npm run dev
```

**Backend**, in a second terminal:

```bash
cd backend
uv sync
uv run uvicorn proofpay.main:app --port 8000
```

Open <http://localhost:5173>.

That is the whole setup. Roughly five minutes on a fresh machine, most of it downloading.

### Two ways to run it

| | when to use it |
|---|---|
| `npm run dev` | The frontend alone, reading committed fixtures. Use this if the backend is broken, mid-change, or you are on a laptop that has never run Python. |
| Set `VITE_USE_MOCKS=false`, then run `npm run dev` | Against the live backend. Use this for the recording, so what the room sees came from the real engine. |

Both show the same five verdicts. The fixtures are generated by running the real engine over the
committed receipts, so mock mode is not a mock-up of the product, it is a recording of it.

For live mode, use the command for the presenter's operating system:

```bash
# Linux / macOS
VITE_USE_MOCKS=false npm run dev
```

```powershell
# Windows PowerShell
$env:VITE_USE_MOCKS='false'; npm run dev
```

### Before recording

Add `?present=1` to the URL: <http://localhost:5173/?present=1>. Type sizes go up for a projector.

Check which URL `npm run dev` printed. The instructions and saved presentation URL use port 5173,
but Vite moves to 5174 if another process already holds that port.

## The five cases

Each demo order has one receipt that belongs to it. The receipts are in `fixtures/demo/images/`.
Pick the order in the picker at the top of the screen, then drop or choose the matching file.

| Order | Receipt | Verdict | What it proves |
|---|---|---|---|
| ORD-G01 | `G01.jpg` | Payment received | The normal case. Most payments are fine and the app says so quickly. |
| ORD-S01 | `S01.jpg` | Amount does not match | The screenshot claims Rs 5,000. Rs 500 arrived. This is the headline. |
| ORD-D01 | `D01.jpg` | Already counted | This payment was already used for another order. No human remembers this. |
| ORD-N01 | `N01.jpg` | Not sure about this one | Rs 1,200 against a Rs 1,500 order. The app refuses to guess. |
| ORD-U01 | `U01.jpg` | No matching payment yet | Not an accusation. The money may simply not have arrived. |

There is also a row of example buttons near the bottom of the upload screen. They replay three of
these with one tap and no file picker. Use them if a file dialog would be awkward on camera.

### An order of telling that works

Lead with S01, not G01. The edited amount is the thing nobody believes until they see it, and it
explains the whole product in one screen. Then D01, because "this payment was already used" is the
one a human genuinely cannot catch. Then G01 to show the normal case is fast and unremarkable, and
U01 to show the app does not accuse people when it simply does not know yet.

N01 is the one to keep if you are short of time and cut if you are not: "the app refuses to guess"
lands well in a Q&A but weakly in a video.

## While recording

**"Start over" is always on screen**, top right, and Escape does the same thing. It cancels whatever
is in flight and returns a clean upload screen. If a take goes wrong, press Escape and start the
sentence again. Do not reload the browser on camera.

Every check holds for about two and a half seconds before the verdict lands, whether the answer took
5ms or 2 seconds. The room sees a rhythm rather than a race, and it is the same on mocks and live.
Do not fill the pause; let it land.

The three counting cells at the bottom open the list of what they count. Tapping one is a good way
to end the demo: it shows the product remembers, which is the argument.

## If something goes wrong

**The picker is empty and nothing can be chosen.** The backend is not up, or not on port 8000. Press
Escape, which refetches the orders. If that does not work, restart the backend. The frontend alone
with `npm run dev` and no env var always works.

**"Check this payment" is greyed out.** You have not picked an order. The line beside the button says
so. This is deliberate: the app will not check a payment against an order nobody chose.

**A verdict says "Could not read this one".** The reader failed rather than the payment. Press "Try
again", which re-runs the same check. This cannot happen on the deterministic path, so if you see it
during a rehearsal, something is configured wrong.

**Everything is slow or a verdict looks wrong.** Check whether `PROOFPAY_RECEIPT_EXTRACTOR=qwen` is
set in `backend/.env`. It should not be for a demo. See below.

## About the Qwen-VL key

**Do not demo on it.** Leave `PROOFPAY_RECEIPT_EXTRACTOR` at its default.

ProofPay reads receipts with Qwen-VL in production, and the adapter is built and wired. But it puts
a network call on the critical path of a live demo, and a rate limit or a slow venue connection
during a recording costs you the take. The deterministic reader gives identical verdicts and cannot
fail.

If you have a DashScope key and want to confirm the cloud path works, run it once, separately:

```bash
cd backend && uv run python ../tools/verify_qwen.py
```

It refuses to run unless it is genuinely talking to DashScope, then compares all five demo verdicts
against the deterministic path. Save the output as evidence. Then put the key away and record on the
default.

## The persisted path

The demo above runs on fixtures. There is a second, database-backed path for the same product, and
it is worth knowing it exists if a judge asks whether any of this is real.

```bash
cd backend
uv run alembic upgrade head
uv run python scripts/seed.py --reset
```

That loads all 30 receipt scenarios into the database and prints a merchant id per case. Those go
through repositories, tenant scoping, real allocations and idempotent replay, and
`backend/tests/test_seed.py` drives five of them over HTTP to prove all five verdicts still come out.

You do not need any of it for the video. It is the answer to "is this a mock-up?"
